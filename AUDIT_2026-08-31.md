# Project Management — Static Audit & Hardening

Date: 2026-08-31
Branch: `chatgpt/audit-jalali-seeders-20260831`
Base: `main`

## Scope

Static review and safe hardening of the Laravel application, with emphasis on:

- database seed safety and repeatability;
- Persian/Jalali date presentation;
- language seed correctness;
- security-sensitive middleware;
- dependency reproducibility;
- basic regression checks.

> Database and API date values intentionally remain Gregorian/ISO-compatible. Jalali conversion is applied in the presentation layer so filtering, integrations, reports, queues, payment callbacks and persistence are not corrupted.

## Fixed

### 1. Critical — `db:seed` rotated `APP_KEY`

`DatabaseSeeder` previously executed `php artisan key:generate` during seeding. Re-running a seeder on an installed application could therefore rotate the encryption key and invalidate encrypted values, cookies and sessions.

**Fix:** key generation was removed from `DatabaseSeeder`. Key generation remains an installation/bootstrap responsibility.

### 2. High — seeding mode could remain enabled after an exception

The application enabled `app.seeding` and only disabled it at the normal end of execution.

**Fix:** seeding now runs inside `try/finally`, guaranteeing reset of `app.seeding` and cache cleanup even when a seeder throws.

### 3. High — large company list loaded at once

Company-scoped seeding previously loaded all companies in one collection.

**Fix:** companies are processed with `chunkById(100)`.

### 4. High — incomplete top-level seed pipeline

`EmailSettingSeeder` existed but was not included in the main seed sequence.

**Fix:** it is now included in `DatabaseSeeder`.

### 5. High — repeat seeding duplicated global records

Several core seeders used unconditional `create`, `insert`, or permission attachment operations.

**Fixes:**

- `CoreDatabaseSeeder`: global settings are created once; language rows and award icons are reconciled safely.
- `EmailSettingSeeder`: notification settings use `updateOrCreate` keyed by slug.
- `RoleSeeder`: Manager role uses `firstOrCreate` and permission relations use `sync`.
- `ProjectAdminRoleSeeder`: role creation is idempotent.

### 6. Medium — invalid English language status

`LanguageSetting::LANGUAGES` contained `diabled` instead of `disabled` for English.

**Fix:** corrected the constant and changed language seeding to `updateOrCreate`, so existing bad seed data is repaired on the next seed run.

### 7. High — brittle Jalali conversion helper

The legacy `ctj()` implementation was tightly coupled to runtime company context and accepted a narrow input shape.

**Fix:** added `app/Helper/jalali.php`, loaded before the legacy helper. It:

- accepts strings, timestamps and `DateTimeInterface` values;
- safely handles CLI/tests/queues where company context may not exist;
- preserves invalid/non-date values rather than throwing;
- provides `ctj_datetime()` and `jalali_date()` aliases;
- converts only when application locale is `fa`;
- keeps persistence/API values Gregorian.

A focused unit test file was added for conversion behavior.

## High-risk findings not blindly changed

### A. Broad CSRF webhook exemptions — High

`VerifyCsrfToken` currently exempts wildcard patterns:

- `*-webhook/*`
- `*_webhook/*`
- `*_webhook`
- `*-webhook`

and public lead/ticket endpoints.

This is broader than ideal. The safe remediation is to enumerate exact webhook routes and verify each provider's signature/HMAC/token before narrowing/removing the exemption. Blindly enabling CSRF on third-party callbacks can break payments and integrations, so this needs route-by-route runtime verification.

### B. Unpinned Composer dependencies — High operational risk

The project uses multiple `*` constraints, at least one `dev-master`, and `minimum-stability: dev`. A clean build may therefore resolve different package versions over time.

Recommended remediation after integration tests:

1. capture a known-good `composer.lock`;
2. replace wildcard/dev constraints with compatible version ranges;
3. run payment, notification, import/export and module smoke tests;
4. upgrade packages in isolated PRs rather than one bulk update.

### C. Full Jalali coverage requires runtime/page verification

The centralized helper makes Jalali conversion safe and consistent for code paths using the date helper. GitHub code search for this repository did not return a complete index, so static search alone cannot prove that every Blade/DataTable/export path uses the helper.

Before production merge, smoke-test the major UI surfaces in Persian locale: dashboard, projects, tasks, attendance, leave, invoices/estimates, contracts, tickets, notices, events, reports and exports. Any direct Carbon/formatter output should be routed through `ctj()`/`ctj_datetime()` for UI only.

## Licensing / commercial activation

The repository contains Worksuite/Codecanyon-oriented code paths. This audit does **not** bypass or disable third-party licensing, purchase-code validation, DRM, or activation controls. Internal application bugs and workflow restrictions can be fixed, but commercial license circumvention is outside this change set.

## Validation status

- PHP syntax of the new centralized Jalali helper was checked with PHP CLI successfully.
- The repository did not contain a GitHub Actions workflow at audit time.
- Existing unit coverage was minimal, so a focused Jalali helper test was added.
- A full Laravel/PHPUnit run was not possible in the audit runtime because the repository/dependencies could not be cloned into that runtime. CI/server execution is therefore required before production deployment.

## Production runbook

On a staging copy first:

```bash
composer dump-autoload
php artisan optimize:clear
php artisan migrate --force
php artisan db:seed --force
php artisan test --testsuite=Unit
```

Then exercise the major Persian UI pages and provider webhooks before production rollout.


## Follow-up completion — 2026-08-31

The remaining repository hardening tasks were completed on a dedicated branch and validated in GitHub Actions before merge:

- confirmed state-changing GET endpoints were converted to POST and their AJAX/form callers updated so normal Laravel CSRF protection applies;
- read-only modal/list/export routes and the authenticated QR clock-in entry route were intentionally not reclassified merely because their names looked mutating;
- broad webhook CSRF patterns were replaced with provider-scoped callback paths; provider-side signature verification remains the second line of defense;
- the legacy root `w` scratch/deployment SQL file was removed and device schema normalization was moved into a guarded Laravel migration;
- direct Composer wildcards were replaced with ranges based on the known-good lockfile, while the device-tracking dev dependency was pinned to its existing commit and Composer minimum stability was tightened to stable;
- repository regression tests now enforce the HTTP-method, CSRF, dependency and migration invariants;
- CI now installs dependencies, runs Composer's locked security audit, executes the unit suite and lints PHP.

The QR attendance route remains GET because the QR code itself is a navigable login/clock-in entrypoint; its controller requires an authenticated user before changing attendance. Converting that URI to POST would make a scanned QR URL unusable without an intermediate confirmation page.
